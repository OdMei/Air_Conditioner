# N647 智能空调毕设完善路线

日期：2026-10-08。定位：课程／毕业设计演示，要求功能完整、界面清楚、便于答辩。

本文是根据当前源码及官方参考项目形成的建议，不代表这些功能已经实现。本轮只增加这份说明，没有修改固件、模拟器或烧录开发板。

## 1. 项目应该做到什么程度

建议围绕“视觉感知 → 可信状态 → 空调策略 → 演示输出 → 界面与实验记录”完成一个可重复验证的系统。题目可表述为“基于 STM32N6 的视觉感知节能空调控制演示系统”。

目前已有摄像头与 NPU、温湿度与光照、红外与按键、LVGL 双页面及共用真实页面的 PC 预览。下一阶段的核心是让每个设置都有明确控制效果，让故障不冒充正常数据，并能解释每次状态变化。先完成这些，再选择网络控制或模型升级作为扩展。

## 3. 推荐实施顺序与验收

### 第一阶段：数据和输入稳定

1. 修复触摸与摄像头争用 PD4／PD14：统一使用板端 I2C2，串行化相机和触摸事务，不通过重新配置 GPIO 抢占总线。校正 ThreadX 优先级，并对相机启动等待、驱动事务增加有界超时及失败降级。
2. 为 AI、温湿度、光照增加有效状态和最近成功采样时间。过期阈值用配置表达，根据实测更新周期选定。只有成功结果才能更新“最近成功时间”。
3. 检查启动、推理和后处理错误路径，错误不能发布为“0 人”。AP3216C 读取应返回状态，失败不解码未初始化数据。
4. 界面显示“人数未知”“温湿度不可用”“光照不可用”和恢复状态。

人员确认还应加入短时间窗或连续有效结果确认，避免单帧漏检切成无人，或单帧误检反复清零无人计时。确认窗口先依据实际采样日志选定，再验证暗光、遮挡与画面边缘场景；它与后续 10／30 分钟策略计时分别处理。

| 故障 | 建议的降级行为 |
| --- | --- |
| AI 失效／过期 | 中断连续无人计时并重新开始确认；暂停基于人数的自动策略，保留用户手动操作 |
| 光照失效 | 停止基于暗光的自动睡眠判断，手动睡眠仍按明确规则执行 |
| 温度失效 | 显示 `--`，不继续用旧温度产生制冷请求；保留设定和操作入口 |
| 摄像头启动异常 | 界面、按键和红外继续工作，显示具体错误，避免等待相机使输入永久停住 |

建议验收：重复冷启动、摄像头与触摸同时工作、连续运行和反复切换页面；断开或注入传感器故障后，页面仍能操作。可把“连续 1 小时运行、20 次冷启动、100 次页面切换”作为第一版回归目标，实际结果要记录。

### 第二阶段：补齐空调控制行为

- 明确 MODE 的业务语义。建议先支持“智能自动／手动制冷”，并明确人员节能策略是否启用；现有数值 0／1 不能直接解释为制冷／制热。
- 统一规则优先级：有效性与必要的输出停止条件、用户关机、明确人工选择、人员策略、温度控制。自动关机后再手动开机应有定义好的新计时或人工优先行为。
- 在现有纯 C 逻辑中加入温度迟滞：高于设定上界才请求制冷，低于下界才结束，中间维持状态。迟滞宽度需要结合当前 DHT11 分辨率选取。
- 定义 SLEEP、ECO、TURBO 对执行目标或风档的实际作用；把用户设定与派生执行值分开显示，例如“设定 26°C／节能执行 28°C”。这只是建议示例，不是当前固件行为。
- FAN 提供 1～5 档选择，按钮具有选中反馈，16／30°C 边界给出明确反馈。
- 启停延时与最小停机时间用非阻塞时钟处理，故障停止和明确关机不应被普通最小运行时长阻挡。毕设中可先展示这些规则，具体设备参数待负载确定后设置。
- 集中计算输出，让开发板与 PC 使用同一份结果。当前 `app.c` 和 `simulator/main.c` 的掩码计算不应继续各自演进。

可以先用板载 LED 标示制冷／风机请求，完成输入到输出的验证；核对可用 GPIO、模块电平和通道映射后，再接低压风机或灯作为演示负载。页面应区分“控制请求”“GPIO 已输出”和“设备反馈”；没有反馈线时不能把 GPIO 状态当作设备已运行的证明。

验收：改目标温度确实改变制冷请求；阈值附近没有反复跳变；手动开机不会立即被旧的无人计时关闭；所有页面及输入方式看到相同的有效状态和输出结果。

### 第三阶段：完成 800×480 用户界面

| 区域 | 推荐内容 |
| --- | --- |
| 顶部约 56 px | 项目名称、电源、实板／模拟数据标识、数据健康状态 |
| 中部左侧 | 48 px 左右的大号目标温度、温度加减，实际温度与湿度卡片 |
| 中部右侧 | 人数、明暗、运行模式、无人计时及当前策略原因 |
| 底部 | 电源、模式、风速、睡眠、摆风、节能按钮及状态反馈 |
| DEBUG 页 | 摄像头画面、检测框、推理更新率、错误码、总线与触摸诊断 |

显示原因比只显示一个状态名更有价值，例如“无人持续达到阈值，进入节能”或“温度无效，制冷请求已停止”。主页面不保留 FT／GT 探测、寄存器和 DMA 地址。

采用项目已经启用的 Flex／Grid 和统一样式，先在 PC 调整，再核对板端。为界面实际用字生成中文字体子集，单独提供大号数字；当前默认 Montserrat 14 不足以支撑中文大字号页面。验证资源占用和反复切页行为，再决定是否调整当前 96 KiB LVGL 内存池。

现在的 `1000 / nn_period_ms` 是推理循环更新率，不应标成摄像头真实帧率。真实推理耗时、摄像头帧率和界面帧率要分别测量。默认模拟模式下的 Camera `-1001` 应解释为未连接硬件；另设明确故障注入场景。

### 第四阶段：做出可以答辩的证据

1. 加入少量事件记录：时间、数据来源、前后状态、执行原因、控制请求。先用串口输出 CSV 和内存环形缓冲即可。
2. PC 预览增加固定场景回放、重置、时间快进和故障注入，共用真实业务逻辑。快进必须标注仿真时间，实板 10／30 分钟阈值不为了演示而悄悄改短。
3. 在调试页恢复最多 10 个人体框及置信度的数据链路，验证推理图与显示图的裁剪、缩放和偏移。当前应用层框副本已删除，恢复可见框时再增加有消费者的数据。
4. 用标注的自采场景测量有人／无人误判、漏检、判定延迟和误关机次数。先评估现有 Tiny YOLO v2，再决定模型升级的必要性。
5. 比较同一输入时间线下的固定运行与人员策略运行：报告负载开启时间；若接入实际功率采样再计算能耗。由假定功率计算的结果必须写“模拟能耗”，不能作为真实空调节电比例。
6. 整理已完成／待完成矩阵，统一 README、设计说明和实际功能。现在文档中的网络语音、Modbus、音频、继电器保护等有些仍是目标，不能混入已完成成果。

### 第五阶段：收尾与扩展

- 保存目标温度、模式和风档等偏好。已有 EEPROM 可以复用，但先修正无限等待和错误返回；记录加入版本、校验和两份备份，延迟保存，避免每次触摸就写。默认重新上电保持关机。
- 固定源码、编译工具、模型配置、三份 HEX 的对应关系；显示版本和模型信息，记录镜像校验值。完成一次从干净构建目录出发的板端完整构建，当前受影响文件重编加历史对象链接还不等同于完整 clean build。
- 后续通信只选一个明确目标，如局域网读取状态与调温，复用已有 action 和快照。语音、Modbus、音频、习惯学习和 YOLO11n 放在基本闭环验收之后逐项选择。

## 5. 五分钟答辩演示脚本

| 环节 | 操作 | 要展示的证据 |
| --- | --- | --- |
| 1. 正常工作 | 识别有人，读取温湿度，手动调温 | 相机、人数、真实数据、按钮和输出请求连成流程 |
| 2. 人员节能 | 有人离开，仿真时间推进到阈值 | 连续可信无人计时、节能和关机原因；标注模拟时间 |
| 3. 人工优先 | 自动关机后再次开机、选择手动模式 | 操作有明确效果，不被旧计时立刻覆盖 |

| 5. 实验结果 | 显示对比日志或导出的曲线 | 误判、响应、开启时长；实测和模拟结果分开解释 |

## 6. 下一轮最小实现包

推荐先实施“数据有效性＋用户页信息整理”：检查 AI／光照错误路径，记录数据时间，界面显示未知或离线，把底层诊断移入 DEBUG，并补充模拟失效场景。然后补温度控制、模式和输出一致性。UI 美化与功能逻辑分别验收，继续共用 PC 和板端源码。

代码组织沿用现有 `app.c`、`app_climate_logic.c`、`app_input_logic.c`、`app_ui.c` 和显示端口；真正接入 GPIO 时再增加有实际职责的输出适配。现有主机测试和预览自检可扩展边界、错误和人工优先场景，无需重新搭建一个框架。
