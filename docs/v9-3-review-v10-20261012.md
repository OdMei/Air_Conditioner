# V9.3 全面梳理与 V10 日常使用方案

日期：2026-10-12。性质：代码审查与下一版设计，尚未实施 V10，也未修改或重新烧录固件。

用户本次澄清：“也不是接入真实空调，就是想让这个产品变得更有实际性。”因此本方案围绕现有 N647、摄像头、LCD、已接 PG3 的 DHT11 和板载资源，设计能独立使用的产品功能。既有文档是参考资料，不代替这次用户要求。

## 1. 当前工程究竟完成了什么

V9.3 是已经运行、编译校验和基础实板验收通过的嵌入式原型。2026-10-12 重新核对发布清单：540 个编译源、1,520 个构建输入；当前输入与冻结版本全部一致，580,576 字节应用 BIN 哈希匹配。40 项工程检查、272 项 PC 界面断言和用户的实板反馈是已有证据，本次没有重复运行这些测试。

| 层次 | 已实现能力 | 能力边界 |
|---|---|---|
| 启动与运行 | FSBL、外部 Flash 模型和应用；ThreadX 分工；界面先启动，相机随后初始化 | 当前有 8 个应用工作线程：显示、输入、传感器、日志、相机、NN、后处理、ISP；SDK 外设例程存在不代表已接入 |
| 图像与 AI | IMX335、ISP/DCMIPP；LCD 800×480，NPU 224×224 RGB；Tiny YOLO v2，单类 person、最多 10 个结果 | 没有姿态、身份、真实睡眠、跌倒或全屋覆盖能力；模型分数不等于准确率 |
| 环境采集 | DHT11 约每 2 秒采集；AP3216C 光照；新鲜度、失效、最后成功值与恢复处理 | 湿度主要用于显示；ALS 为原始计数，未标定为 lux；没有 CO₂、污染物或用电测量 |
| 规则与输入 | 触摸、按键、红外统一动作；温控迟滞、30 秒演示停机保护、手动/自动偏好、无人 10/30 分钟规则 | 四路输出只是软件请求，没有负载；有人且暗推断的 SLEEP 不是识别到睡眠 |
| 界面 | 中文主页、控制弹层、原始/稳定框、可收起诊断、曲线大图和点选读数 | 稳框只调整显示，不改善模型检出率，不参与人员判定；隐藏视频不等于停用摄像头 |
| 历史与时间 | 5 秒采样、60 点、12 条事件；来源会话、实际采样时间、缺测空点 | 约 5 分钟短期 RAM 历史；断电丢失；尚无可信日历时间与日摘要 |
| 电脑验证 | 共用 UI/规则、鼠标输入、故障注入、场景回放、时间加速 | 电脑模拟不证明真人场景准确性、实板稳框改善幅度或长期可靠性 |
| 运行恢复 | 触摸/共享总线恢复、DHT 重读、ALS 重探测、相机/管线部分恢复与诊断 | 没有整机硬件看门狗运行路径；同步 NPU 调用卡住的自动恢复尚无完整证据 |

已知实板结论是温湿度、画面、触摸和新增操作正常。V9.3 的实板 FPS、AI Hz、稳框 RMS、DHT 成功率及 24 小时稳定性均未测量。历史版本约 30 Hz 的反馈不能直接作为本版新测量。

V9.3 PC LVGL 检查结束时空闲 12,168 字节，最大连续块 6,400 字节，使用的是共享 96 KiB 配置。后续应复用页面和图表，不一次建立大量常驻面板；长历史数据放业务层的有界存储，不挤入 LVGL 分配器。

## 2. 为什么生活用途尚未成立

核心问题是用户日常任务尚不明确。目前主页围绕目标温度、风档、摆风等软件请求组织；没有实际设备执行时，这些操作不能改变房间环境。摄像头和温湿度已经有真实数据，但还不能主动回答“现在有什么值得处理的问题、持续多久、处理过没有、后来恢复没有”。

### 2.1 必须先澄清的检测范围

在当前默认 IMX335 2592×1944 配置下：

- LCD 裁切为 `(0,195,2592,1555)`。
- NN 裁切为 `(324,0,1944,1944)`。
- NN 与 LCD 的水平重合范围约为 `x=100..699`，即中间 600 像素；左右各约 100 像素有画面但未进入 NN。
- NN 上下还包含 LCD 裁掉的内容，因此后处理人数可能增加，但屏幕没有相应可画框。

这不是左右送风分区功能，也不是框坐标映射错误；是两条管线采用了不同可见范围。需要安装检查页、分析范围说明，并研究一致的预处理。当前 `CMW_Aspect_ratio_fit` 是横纵独立缩放，不能直接当成 letterbox 补边。

证据：[app_camera.c](D:/Learning/AC-N647/Air_Conditioner/Air_Conditioner/Project/Project/Air_Conditioner/Appli/Core/Src/app_camera.c:434)、[几何测试](D:/Learning/AC-N647/Air_Conditioner/Air_Conditioner/tests/test_camera_geometry.c:8)、[原始人数与显示框发布](D:/Learning/AC-N647/Air_Conditioner/Air_Conditioner/Project/Project/Air_Conditioner/Appli/Core/Src/app.c:834)、[fit 实现](D:/Learning/AC-N647/Air_Conditioner/Air_Conditioner/Middlewares/STM32_MW_CAMERA/cmw_utils.c:53)。

日常页面只承诺“视野内检测到人体”“持续未检出”“检测不可用”。零检出不能推出整间房无人；暗光不能推出睡眠；黑画面只能提示图像不适用，不能单凭亮度断定镜头被遮住。

### 2.2 其它直接影响使用的缺口

| 缺口 | 当前依据 | 对使用者的影响 |
|---|---|---|
| 在场确认没有独立报告计数 | `app_climate_logic.c:101–147` 在 500 ms 规则周期中按人数和经过时间确认，未消费 frame_id | 同一份仍新鲜的报告可能参与多次确认；短时门限不能证明静坐、背身或遮挡可靠 |
| 环境异常没有生命周期 | 湿度仅参与质量判断；快照无提醒确认/暂缓状态 | 用户要一直看数字，无法主动获得可处理提示 |
| 历史短、事件偏调试 | `app_history.h:7–13`；事件显示十六进制请求码 | 不能回答今天偏湿多久、何时提醒、是否已处理 |
| 配置重启丢失 | `app.c:210` 初始化默认偏好 | 每次上电重新设置，不适合固定摆放长期使用 |
| RTC、存储和网络未接入 | 最终构建未编译 EEPROM/RTC/SD NAND/NetX 等业务；相应 HAL 宏关闭 | 没有真实日期、掉电记录或局域网查看 |
| 常亮与隐私不明确 | `app_lcd.c:91` 开背光；退出 DEBUG 仍采集/推理 | 夜间打扰，用户不能明确停用视觉 |
| 整机持续使用未验收 | IWDG/WWDG 未接入，异常处理有永久循环 | 页面能点并不证明可以连续工作一天 |

## 3. 推荐定位：离线房间环境与在场助手

首个具体场景是书桌或卧室：用户把设备放在固定位置，设置自己接受的温湿度范围。设备识别持续异常，结合视野内在场情况选择合适的提示方式，支持确认和暂缓，记录异常与恢复，便于回顾。

这一定位的差异点是“环境异常持续性、视觉情境、提醒处理结果和可回顾记录”共同工作。是否有实际价值，要用日常使用反馈验证；功能数量和算力利用率不作为产品价值指标。

```mermaid
flowchart LR
    A[真实采样与数据质量] --> B[持续异常与在场判断]
    B --> C[屏幕提示与低打扰策略]
    C --> D[用户确认或稍后提醒]
    D --> E[恢复与事件记录]
    E --> F[本次运行或当日摘要]
```

举例仅表示未来交互，不是实测或通用健康标准：用户设湿度上限 70%、持续 10 分钟才提醒。设备可以显示“超过您设置的湿度上限，已持续 12 分钟”，提供“已知道 / 稍后提醒 / 调整范围”。环境恢复后记录恢复，而不是每两秒弹同一条消息。

摄像头的作用是提供可信的视野内在场情境，例如有人时给出温和提示，未检出时减少声音打扰。环境异常的记录不因暂时漏检、离开视野或主动停用摄像头而清空。检测未知时采用用户选择的保守提示方式。

默认主页显示当前温湿度、观测质量、待处理提醒、记录入口和设置；既有空调逻辑保留到“实验/控制演示”页面，避免破坏已验证代码。DEBUG 仍是排查和安装辅助入口。

## 4. V10 功能优先级

| 优先级 | 功能 | 可交付结果 |
|---|---|---|
| P0 | 可信感知与安装检查 | 分清画面和检测覆盖；按独立报告确认；“检出/观察中/持续未检出/未知”状态；图像或数据不适用时不累计确定无人 |
| P0 | 持续环境提醒 | 用户范围、进入/恢复迟滞、持续确认；提醒、确认、暂缓和恢复完整状态；失效单独显示，旧值不推进异常计时 |
| P0 | 日常主页 | 真实环境和待办提醒为主；旧软件控制转二级入口；操作说明清楚且不重复弹窗 |
| P0 | 配置保存 | 范围、持续时间、提醒偏好、息屏时间断电后恢复；格式版本、校验、坏数据默认回退和保存状态 |
| P1 | 长周期记录 | 保留现有短曲线，增加分钟汇总、异常/未知时长和事件处理结果；先做本次运行，再补日历时间与持久日志 |
| P1 | 低打扰与真正隐私 | 空闲息屏、首次触摸只唤醒；确认提醒后停止重复提示；主动停用采集/推理，温湿度继续运行 |
| P1 | 系统健康监督 | 关键线程进度、重启原因、失效降级；局部视觉故障不导致环境服务重启风暴；看门狗按真实服务前进情况喂养 |
| P2 | 局域网状态与导出 | 本地使用稳定后，再通过以太网只读查看状态/摘要；没有网络时核心功能仍工作 |

环境提醒范围是用户偏好；没有相关传感器时不输出 CO₂、空气质量、实际耗电或必须通风等结论。在场统计不解释成某个人的久坐或睡眠时长。模型升级应由场景误检、漏检和覆盖测试决定。

## 5. 实施结构与资源约束

以下模块名是设计建议，不表示已有代码：

- `app_observation`：统一原始采样、来源、时间与质量，提供独立于 LVGL 的业务输入。
- `app_presence_estimator`：消费原始帧号、采集时间、检测报告和场景可用性。绘图平滑结果不作为输入。
- `app_alert_logic`：纯 C 提醒规则与生命周期；PC/板端共用，用户确认也是明确事件。
- `app_room_history`：分钟聚合、环境状态持续时间、提醒事件和有效覆盖；不能依赖页面是否正在绘制。
- `app_settings_store`：后台有界保存与恢复；UI 只提交保存意图，不直接等 EEPROM。
- UI：只消费快照、显示结果和产生用户事件；复用原有页面、对象和字体生成流程。

当前短期历史在 `app_ui_insights` 中观察快照。新增长期统计和提醒应移到业务服务；息屏或页面渲染故障不应停止它们。后台数据交给 UI 时要提供稳定快照或有界复制，不能让触摸游标持有正在被后台覆盖的环形缓冲指针。

| 资源 | 适合用途 | 接入前要完成的事 |
|---|---|---|
| 已接 DHT11/板载 ALS | 温湿度监测与相对明暗 | 保留成功时间/失效信息；ALS 不直接写 lux；阈值可调整 |
| 摄像头/NPU | 视野内在场辅助 | 覆盖说明、真人场景验证、独立报告确认；隐私停用要协调采集/推理/恢复流程 |
| 板载 EEPROM | 少量配置 | 当前驱动读不回传错误、写忙等待无界；先改超时/状态。与 ALS 共用 I2C4，串行化后台事务。版本/CRC/双副本/去抖保存，避开通用触摸遗留 40～52 字节区域 |
| RTC | 日历时间和安静时段 | 当前未启用；例程固定初始日期不能当实时时间。提供校时和时间有效性；后备电池条件未确认 |
| 板载 SD NAND | 持久事件与长期摘要 | 当前没有文件系统业务。先只读探测和规划分区，不自动格式化、不覆盖未知数据；追加记录要考虑异常断电和空间用尽 |
| 用户 LED/蜂鸣器 | 可选本地提醒 | LED 已有 GPIO；蜂鸣器尚未接入。非阻塞节奏、静音、确认、去重；提醒不以声音为唯一出口 |
| LCD 背光 | 空闲息屏与唤醒 | 当前 brightness 函数只支持开/关；连续百分比调光需另做 PWM，不承诺传入 30 就得到 30% 亮度 |
| USB_UART | 初期 CSV 导出 | 已有有界发送队列；接收业务当前关闭，不能称为已有远程配置接口 |
| 以太网 | 后续只读状态页 | 硬件有接口，当前应用没有网络服务；网线与连接未确认，不作为离线核心功能前提 |

正点原子官方说明确认板载 EEPROM、SD NAND、以太网等资源，现有板卡能提供配置与长期记录的硬件基础；需要接入软件，而不是默认它们已经工作。[开发板资源说明](https://wiki.alientek.com/docs/Boards/STM32/DNN647/start-guide/stm32n647-board-introduction/)

第一期可用有界 RAM 分钟记录加 USB_UART 导出，无需假定已插 SD 卡；持久日志优先研究板载 SD NAND。现用 NOR Flash 承载 FSBL、应用和模型，日志不能随意写入同一区域。

## 6. 下一版拆成两个可验收交付

**V10.0：日常闭环。** 可信描述/安装说明、基于有效新报告的在场辅助、环境持续异常提醒、确认/暂缓/恢复、可调配置及掉电保存、本次运行分钟摘要、基本息屏/唤醒。先用屏幕和可选 LED 提示。真隐私暂停以实际采集和推理停用为验收，若暂停链路未完成则明确只提供“隐藏视频”。

**V10.1：长期生活记录。** RTC 校时与时间有效性、板载 SD NAND 持久事件、当日/多日摘要、系统监督及复位原因、长期运行验收；之后再评估以太网只读查看。若存储和 RTC 尚未接入，V10.0 不宣称已经具有“今日记录”和断电历史。

这两个交付是下一版建议范围。本次完成审查与设计，V10 尚未实现；当前运行与验证基线仍为 V9.3。

## 7. 从功能验收升级到日常使用验收

| 验收 | 建议方法与通过条件 |
|---|---|
| 提醒规则 | 短于持续确认时间的越界不提醒；连续越界在一个采样周期加一个规则周期内提示；阈值附近按迟滞稳定 |
| 处理闭环 | 同一事件确认/暂缓期间不重复弹窗；暂缓到期、环境恢复、用户改范围均有明确结果 |
| 缺测 | DHT 或 AI 失效时显示对应未知；缺测不累计正常/异常/确定无人；恢复后重新确认 |
| 人体场景 | 空画面、海报、静坐、背身、移动、多人遮挡、左右边缘、暗光；记录人工人数、检出比例、误检/漏检片段、确认延迟与未知占比 |
| 配置 | 模拟每个写入阶段断电和 CRC 损坏，选择完整旧副本或明确默认回退；板端重复断电20次验证保存/恢复，不阻塞触摸 |
| 息屏/隐私 | 100 次唤醒检查首次触摸不执行隐藏按钮；停用视觉后确实停止采集/推理，环境服务继续，恢复和健康监督不互相冲突 |
| 记录正确性 | 正常/异常/未知时长与观测区间一致；实际时间、重启、来源和校时边界可解释；回读持久记录验证校验和完整性 |
| 连续使用 | 固定摆放24小时，记录传感器覆盖率、误提醒、触摸错误、重启、内存和恢复结果；再做一周实际使用，判断提示是否值得用户处理 |

真人场景中，如果静坐/遮挡表现不够稳定，先调整摆位和感知判定，再评估换模型。一次界面反馈、软件百万断言和推理率不能替代场景检出验证。

## 8. 值得借鉴的外部实现

- **Home Assistant Alert**：区分问题存在、用户已确认和问题恢复，支持提醒间隔。可借鉴提醒生命周期，用本地纯 C 实现；不要求在板卡上安装 Home Assistant。[官方说明](https://www.home-assistant.io/integrations/alert/)
- **ESPHome Binary Sensor**：提供分别确认 ON/OFF 的时间过滤与失效状态，适合参考新报告与在场状态的边界；具体时间需本项目实测决定。[官方说明](https://esphome.io/components/binary_sensor/)
- **littlefs**：提供掉电恢复及写入提交方面的设计，可借鉴“完整提交才算保存”的原则。不能据此断言现有 SD NAND/FAT 或 EEPROM 已具备同等保障；后端驱动和介质特性要单独验证。[官方项目](https://github.com/littlefs-project/littlefs)

建议首先实现并验证“偏湿/偏热持续异常 → 确认/稍后 → 恢复 → 记录”这一条真实用途，再扩展记录和联网。摄像头是否值得持续开启，应由它改善提示时机和用户体验的效果来证明。
